# 2026-09-05 waypoint validation OOM incident

All times KST. The user reported that VS Code had been forcibly terminated.

## Confirmed evidence

- 08:36:13: the first complete 10 s video replay entered `SimulationApp.close`.
  Its 2,000 physics samples, video and report were saved. It did not climb the stair.
- The local Isaac Lab `SimulationContext._app_control_on_stop_handle_fn` renders
  in a loop until Play is pressed after a stop event. Closing the app can enter
  that loop. The CLI previously left the callback registered.
- A subsequent replay and Firefox UI verification were started without confirming
  that the completed simulator had exited.
- 08:45:56: kernel global OOM. Free swap was 28 kB out of 4,194,300 kB.
  Python PIDs 2838431 and 2840204 had RSS 1,262,007 and 852,722 pages respectively
  (approximately 4.81 GiB and 3.25 GiB at 4 KiB/page; shared pages can overlap).
- Kernel killed Python PID 2838431. Its memory cgroup was
  `app-org.chromium.Chromium-413538.scope`, which also contained VS Code PID 413538.
- 08:47:26: user systemd explicitly logged `Killing process 413538 (code) with
  signal SIGKILL` and `Failed with result 'oom-kill'` for that scope.
- 09:20:43: VS Code restarted.
- At the 09:22 investigation there were no waypoint replay/training GPU processes
  remaining; available RAM was about 8.1 GiB. No GPU Xid error was found in the
  inspected 08:25–09:22 kernel log window.

This was host RAM/swap exhaustion, followed by termination of the parent editor's
execution group. The agent's overlapping heavy verification processes contributed
to the exhaustion. Failure to verify simulator exit before launching the next run
was an execution error. Virtual memory size is not physical RAM use.

## Changes made after the incident

- Unregister simulation callbacks and clear the context before app shutdown.
- Add an exclusive lock before Isaac Sim import, retained through process exit.
- Refuse startup with less than 6 GiB available RAM.
- Recommended launcher uses a separate user systemd scope, MemoryHigh=5 GiB,
  MemoryMax=6 GiB, MemorySwapMax=256 MiB and OOMPolicy=stop.
- Bound replay wall time to 600 s, then TERM/KILL grace of 10 s.
- Run one simulator at a time and confirm process exit; no simultaneous browser
  rendering during simulation verification.

Seven CPU tests passed, including duplicate-process locking and low-memory rejection.
A `true` command verified support for the systemd scope/cap options without GPU use.
Post-incident bounded validation:

- 09:37: corrected initial root and shoulder states confirmed; 2,000 transitions
  had exactly matching adjacent next-state/pre-state values. Non-rendered scope
  peaked at 3,963,731,968 bytes (3.69 GiB). Remaining native teardown delay prompted
  an additional 15 s cleanup watchdog. This scope was explicitly stopped before
  the next simulation was launched.
- 09:39:16–09:40:02: one rendered replay completed with process exit code 0; scope
  became inactive and no waypoint GPU process remained. Final outputs are in
  `waypoint_runs/2026-09-05_09-39-42_554503/`: 200 frames / 10 s, 2,000 physics
  samples, valid NPZ/CSV/JSON, exact state continuity. Jump result was false.
- Available RAM after final exit was about 9.1 GiB. No concurrent browser was
  launched for these post-incident simulation tests.
- 21:17:33: another rendered replay saved all outputs but hung in native
  `SimulationApp.close()` while holding about 5 GiB. The Python-thread watchdog
  could not run because native cleanup retained the GIL. The isolated scope was
  stopped without affecting VS Code. The CLI now skips native Kit cleanup after
  flushing all result files and terminates directly with the intended exit code.

The pre-incident video is not evidence that the final fixes passed; use the
09:39 replay for that purpose. The cleanup watchdog records its fallback if
Python remains alive; Kit can also exit natively before Python post-close code.
